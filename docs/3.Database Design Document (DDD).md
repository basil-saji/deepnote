# 1. Introduction

This document describes the database architecture of DeepNote v0.1.

DeepNote follows a hybrid storage architecture.

- **TXT files** are the primary storage (Source of Truth).
- **PostgreSQL** stores metadata and semantic index information.
- **pgvector** stores vector embeddings and performs semantic similarity search.

The database is **not** used to store complete note contents. The first AI chat version uses the active editor buffer as temporary prompt context and keeps messages in memory; it adds no chat tables or columns.

---

# 2. Database Objectives

The database is responsible for:

- Storing note metadata
- Managing categories
- Storing semantic chunks
- Storing vector embeddings
- Supporting semantic search
- Maintaining indexing metadata

---

# 3. Database Architecture

```
             TXT Files
        (Source of Truth)
               │
               │
      Semantic Indexing
               │
      ┌────────┴────────┐
      │                 │
      ▼                 ▼
 PostgreSQL        pgvector
 (Metadata)     (Embeddings)
```

TXT files contain the actual note contents.

PostgreSQL stores only searchable metadata and semantic index information. The active note may be passed directly from the editor buffer to the local chat service; this does not create a duplicate persistent copy in PostgreSQL.

# 5. Database Normalization

The schema follows **Third Normal Form (3NF).**

## First Normal Form (1NF)

- Atomic values only.
- No repeating groups.

Example:

- One category per row.
- One chunk per row.

---

## Second Normal Form (2NF)

Every non-key attribute depends entirely on its primary key.

Example:

Chunk information depends only on `chunk_id`.

---

## Third Normal Form (3NF)

No transitive dependencies exist.

Example:

Categories are stored separately and referenced using foreign keys.

# 6. Database Tables

## 6.1 Categories Table

Stores available note categories.

| Column | Type | Description |
|----------|------|-------------|
| category_id | UUID | Primary Key |
| name | VARCHAR(100) | Category Name |

### SQL

```sql
CREATE TABLE categories (
    category_id UUID PRIMARY KEY,
    name VARCHAR(100) NOT NULL UNIQUE
);
```

---

## 6.2 Notes Table

Stores note metadata.

| Column | Type | Description |
|----------|------|-------------|
| note_id | UUID | Primary Key |
| title | VARCHAR(255) | Note Title |
| file_path | TEXT | TXT File Location |
| indexed_content_hash | CHAR(64) | Last Indexed SHA-256 |
| category_id | UUID | Foreign Key |
| index_version | INT | Index Schema Version |
| last_indexed_at | TIMESTAMP | Last Successful Index |
| created_at | TIMESTAMP | Created Time |
| updated_at | TIMESTAMP | Modified Time |

### SQL

```sql
CREATE TABLE notes (

    note_id UUID PRIMARY KEY,

    title VARCHAR(255) NOT NULL,

    file_path TEXT NOT NULL,

    indexed_content_hash CHAR(64),

    category_id UUID,

    index_version INT DEFAULT 1,

    last_indexed_at TIMESTAMP,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_category
        FOREIGN KEY(category_id)
        REFERENCES categories(category_id)

);
```

---

## 6.3 Note Chunks Table

Stores semantic chunks and their embeddings.

Each row represents one indexed chunk.

chunk_text is stored to generate previews and locate the matching section after opening a note.

| Column | Type | Description |
|----------|------|-------------|
| chunk_id | UUID | Primary Key |
| note_id | UUID | Parent Note |
| chunk_index | INT | Chunk Order |
| chunk_text | TEXT | Chunk Content |
| embedding | VECTOR(768) | Embedding Vector |

### SQL

```sql
CREATE TABLE note_chunks (

    chunk_id UUID PRIMARY KEY,

    note_id UUID NOT NULL,

    chunk_index INT NOT NULL,

    chunk_text TEXT NOT NULL,

    embedding VECTOR(768),

    CONSTRAINT fk_note
        FOREIGN KEY(note_id)
        REFERENCES notes(note_id)
        ON DELETE CASCADE,

    CONSTRAINT uq_chunk_order
        UNIQUE(note_id, chunk_index)

);
```


---

# 9. Vector Index

Semantic search uses pgvector's HNSW index.

```sql
CREATE INDEX idx_chunks_embedding

ON note_chunks

USING hnsw

(embedding vector_cosine_ops);
```

Purpose:

- Fast semantic search
- Approximate nearest neighbour retrieval
- Low search latency

The default HNSW parameters are used in v0.1.

---

# 10. Atomic Indexing Transaction

Whenever a modified note is indexed, the complete database update is executed inside a single transaction.

Workflow

```
Read TXT

↓

Generate Chunks

↓

Generate Embeddings

↓

BEGIN TRANSACTION

↓

Delete Previous Chunks

↓

Insert New Chunks

↓

Update Hash

↓

Update Index Version

↓

Update last_indexed_at

↓

COMMIT
```

Failure

```
Any Error

↓

ROLLBACK

↓

Previous Index Remains Valid
```

This guarantees that notes are never left partially indexed.

---

# 11. Semantic Search Query

Example SQL

```sql
SELECT

    note_id,

    chunk_text,

    embedding <=> ? AS distance

FROM note_chunks

ORDER BY embedding <=> ?

LIMIT 20;
```

The application then:

1. Groups matching chunks by note.
2. Applies the ranking algorithm.
3. Displays the highest ranked notes.

---

# 12. Search Ranking

DeepNote ranks notes rather than individual chunks.

```
Final Score

=

Best Chunk

+

0.05 × Second Best

+

0.02 × Third Best
```

Only chunks above the configured similarity threshold contribute to the final score.

# 13. Data Integrity

The database enforces:

- Primary Keys
- Foreign Keys
- NOT NULL Constraints
- UNIQUE Category Names
- UNIQUE(note_id, chunk_index)
- ON DELETE CASCADE

These constraints maintain consistency and prevent duplicate or orphaned records.

---

# 14. Storage Strategy

## TXT Files

Store:

- Complete note contents

TXT files remain the **Source of Truth**.

---

## PostgreSQL

Stores:

- Note metadata
- Categories
- Semantic chunks
- Embedding vectors

Complete note contents are **not** stored in the database.

---

# 15. Future Scalability

The schema supports future enhancements such as:

- Rich text editing
- PDF indexing
- OCR
- Voice notes
- Multiple embedding models
- Plugin architecture

Persistent chat history or multi-note AI retrieval, if introduced later, will require separate design work. Neither is part of the initial active-note chat feature.

The `index_version` field allows notes to be re-indexed if the embedding model or chunking strategy changes in future versions.

---

# 16. Database Design Decisions

| Decision | Reason |
|----------|--------|
| TXT files as Source of Truth | Users retain ownership of notes |
| PostgreSQL stores metadata only | Lightweight hybrid architecture |
| pgvector | Efficient semantic similarity search |
| Chunk-based indexing | Better retrieval accuracy |
| chunk_text | To generate previews and locate the matching section after opening a note |
| HNSW index | Fast vector search |
| SHA-256 hash | Detect content changes |
| Transactions | Prevent partial indexes |
| No chat tables in v0.1 | Active-note conversation remains in memory; no schema change is required |
| index_version | Future schema migration |
| 3NF normalization | Reduce redundancy |
| ON DELETE CASCADE | Automatic cleanup |

---

# 17. Conclusion

DeepNote combines portable TXT files with PostgreSQL and pgvector to provide efficient offline semantic search.

The database follows normalization principles, maintains transactional consistency, and supports future extensibility while remaining simple enough for an academic Object-Oriented Programming project.
