# 1. Introduction

This document defines the coding standards and conventions followed during the development of DeepNote.

The objectives are:

- Maintain consistent coding style
- Improve readability
- Simplify debugging
- Encourage modular design
- Improve maintainability

These guidelines should be followed throughout the project.

---

# 2. General Principles

- Prefer readable code over clever code.
- Keep methods short and focused.
- Follow the Single Responsibility Principle.
- Avoid duplicate code.
- Use meaningful names.
- Separate business logic from UI code.
- Write code that is easy to explain during project evaluation.

---

# 3. Naming Conventions

## Packages

Use lowercase names.

Examples

```text
com.deepnote.model
com.deepnote.dao
com.deepnote.service
com.deepnote.controller
com.deepnote.ui
com.deepnote.util
```

---

## Classes

Use PascalCase.

Examples

```java
Note
Category
Chunk
NoteService
SearchService
HashUtil
MainWindow
```

---

## Interfaces

Use PascalCase, without an `I` prefix.

Examples

```java
Searcher
```

Implementations are named after the strategy they provide, not the interface:

```java
VectorSearcher
TextSearcher
```

---

## Methods

Use camelCase and begin with a verb.

Examples

```java
saveNote()

createNote()

deleteNote()

calculateHash()

generateEmbeddings()

searchNotes()
```

---

## Variables

Use camelCase.

Examples

```java
noteTitle

chunkIndex

searchResults

currentHash

embeddingVector
```

Avoid meaningless names like:

```java
tmp

str1

abc

obj
```

---

## Constants

Use uppercase with underscores.

Examples

```java
DEFAULT_CHUNK_SIZE

DEFAULT_BATCH_SIZE

SIMILARITY_THRESHOLD

MAX_RETRY_COUNT
```

---

## Boolean Variables

Use descriptive names.

Examples

```java
isDirty

hasChanges

isIndexed

isSemanticSearchAvailable
```

# 5. Class Design Guidelines

Each class should have a single primary responsibility.

Good example

```
HashUtil

↓

Only computes SHA-256 hashes.
```

Avoid combining unrelated responsibilities into one class.

---

# 6. Method Design Guidelines

Methods should:

- Perform one task only.
- Return early where appropriate.
- Avoid deep nesting.
- Be easy to understand.

Example

```java
public void saveNote() {

    if (note == null)
        return;

    ...

}
```

Methods should generally remain under 40–50 lines where practical.

# 8. Comments

Comments should explain **why**, not **what**.

Good

```java
// Skip indexing because the note content has not changed.
```

Avoid

```java
// Increment i
i++;
```


# 9. Exception Handling

Never ignore exceptions.

Bad

```java
try {

}
catch (Exception e) {

}
```

Good

```java
try {

}
catch (SQLException e) {

    logger.error("Database operation failed.", e);

}
```

Prefer specific exception types.

Examples

- IOException
- SQLException
- FileNotFoundException

Avoid catching generic `Exception` unless necessary.

Custom exceptions should represent application-specific failures rather than reusing generic Java exception types.

Example

```java
NoteIndexingException
```

This distinguishes an indexing failure from an ordinary `IOException` or `SQLException`, and lets the UI display a meaningful message while note editing continues normally.

# 10. Logging

Use structured logging.

| Level | Usage |
|--------|-------|
| INFO | Normal application events |
| WARNING | Recoverable problems |
| ERROR | Unexpected failures |

Examples

```
INFO
Application started.
```

```
INFO
Note indexed successfully.
```

```
WARNING
Semantic search unavailable. Falling back to keyword search.
```

```
ERROR
Failed to connect to PostgreSQL.
```

Never log passwords or sensitive configuration values.

# 11. File Handling

TXT files are the Source of Truth.

Always:

- Use try-with-resources.
- Validate file existence.
- Handle I/O exceptions.
- Close resources properly.

Example

```java
try (BufferedReader reader = Files.newBufferedReader(path)) {

    ...

}
```

---

# 12. Database Guidelines

- Use PreparedStatement.
- Avoid SQL injection.
- Use batch inserts where appropriate.
- Execute indexing inside a transaction.
- Close JDBC resources properly.

Always use:

```java
Connection

PreparedStatement

ResultSet
```

inside try-with-resources blocks whenever possible.

---

# 13. Hashing Guidelines

SHA-256 is used to detect content changes.

Rules

- Compare hashes instead of full note contents.
- Skip indexing if the hash is unchanged.
- Update the stored hash only after successful indexing.

---

# 14. Semantic Search Guidelines

- Perform vector search first.
- Fall back to keyword search if semantic search is unavailable.
- Group chunk results by note.
- Apply the note ranking algorithm before displaying results.
- Store chunk text for search previews and note navigation.

`SearchService` delegates to the appropriate `Searcher` implementation rather than implementing search logic itself.

- `VectorSearcher` performs semantic search.
- `TextSearcher` performs keyword fallback.

---

# 15. SwingWorker Guidelines

Semantic indexing should run using `SwingWorker`.

Guidelines

- Never block the Swing Event Dispatch Thread (EDT).
- Trigger indexing only after a successful save.
- Update the status bar in the `done()` method.
- Skip indexing if the note hash has not changed.
- Keep UI updates on the EDT.

---

# 16. Configuration Guidelines

Avoid hardcoding configurable values.

Store settings inside the application configuration.

Examples

```text
chunk.size=500

chunk.overlap=50

embedding.batch.size=32

semantic.threshold=0.80

telemetry.enabled=false
```

# 17. Git Conventions

Recommended commit format

```text

```

Keep each commit focused on one logical change.

# 18. Code Review Checklist

Before committing code:

- Code compiles successfully.
- No unused imports.
- No commented-out code.
- Methods have meaningful names.
- Exceptions are handled properly.
- Resources are closed.
- Logging is appropriate.
- Formatting is consistent.
- Business logic is not placed inside UI classes.

---

# 19. Best Practices

✔ Follow SOLID principles where appropriate.

✔ Prefer composition over unnecessary inheritance.

✔ Keep SQL inside DAO classes.

✔ Keep AI-related logic inside `IndexService`, `SearchService`, and the `Searcher` implementations.

✔ Keep Swing classes responsible only for the user interface.

✔ Write code that is easy to understand and maintain.

# 20. Conclusion

# 19.1 Local AI Chat Guidelines

- Keep AI chat optional and separate from the ordinary semantic-search path.
- Scope every request to one active note. Use the current editor buffer where feasible so unsaved edits are not ignored.
- Do not mix messages or note context across editor tabs.
- Keep a bounded number of recent turns in memory for follow-up questions; persistent history is out of scope for the first version.
- Check the note, conversation and prompt against a configurable context budget. Never silently truncate content while claiming the model saw the whole note.
- Use a local Ollama-compatible generative model. EmbeddingGemma remains the search embedding model and is not the chat generator.
- Never wait for local model inference on the EDT; use SwingWorker or equivalent background execution and update Swing components on the EDT.
- Show meaningful model-unavailable, timeout and context-limit messages. Do not send private note content to a cloud service as a fallback.
- The grounding prompt should require the model to acknowledge when the note does not support an answer. Do not treat prompt grounding as a guarantee against hallucinations.
- Collapsing the sidebar hides the view but must not clear the in-memory conversation.

---

Following these coding standards helps keep DeepNote readable, modular, and maintainable.

The conventions encourage clean object-oriented design, proper separation of concerns, and consistent implementation practices while remaining appropriate for an academic Object-Oriented Programming project.
