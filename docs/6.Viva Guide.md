# 1. Introduction

This guide contains the important concepts, design decisions, trade-offs and commonly asked viva questions for DeepNote v0.1.

Its purpose is to help explain the project confidently during demonstrations and viva examinations.

---

# 2. Elevator Pitch (30–60 Seconds)

> DeepNote is an offline AI-powered semantic note-taking application built using Java. Unlike traditional note-taking applications that rely only on keyword search, DeepNote uses vector embeddings generated locally using EmbeddingGemma through Ollama. Notes are stored as normal TXT files, while PostgreSQL with pgvector stores only metadata and vector embeddings, enabling semantic search without storing complete note contents in the database.

---

# 3. Project Objective

> To develop an offline desktop note-taking application that supports semantic search using locally generated vector embeddings.

---

# 4. Why This Project?

Traditional note-taking applications depend mainly on keyword matching.

Example

Searching

```
Vehicle
```

may not find

```
Car
```

DeepNote searches based on meaning rather than exact words.

# 7. Why TXT Files?

TXT files are

- Portable
- Human readable
- Easy to edit outside DeepNote
- Easy to back up

TXT files remain the **Source of Truth**.

# 8. Why PostgreSQL?

PostgreSQL stores

- Note metadata
- Categories
- Semantic chunks
- Embeddings

It also supports the **pgvector** extension required for semantic search.

---

# 9. Why pgvector?

pgvector allows similarity search directly inside PostgreSQL.

Instead of comparing words, it compares embedding vectors.

---

# 10. Why Not Store Notes in PostgreSQL?

The complete note is stored as a TXT file because

- Users own their files
- Files remain portable
- Easier backup
- Database stays lightweight

---

# 11. Why Store Embeddings in PostgreSQL?

Embeddings need

- Fast similarity search
- Vector indexing
- Metadata association

TXT files alone cannot perform semantic search efficiently.

---

# 12. Why LangChain4j?

LangChain4j is used as a utility library for

- Recursive chunking
- Token counting
- Embedding model integration

It does **not** control our application architecture.

---

# 13. Why EmbeddingGemma?

Reasons

- Lightweight
- Runs locally
- Excellent retrieval performance
- Supported by Ollama
- Generates 768-dimensional embeddings

---

# 14. Why Ollama?

Ollama runs AI models locally.

Benefits

- Offline
- Private
- No API costs
- Fast local inference

---

# 15. Why Semantic Search?

Keyword search requires exact words.

Semantic search retrieves notes based on meaning.

---

# 16. Why Chunking?

A long note should not become one embedding.

Instead

```
Note

↓

Chunks

↓

Embedding per Chunk
```

Benefits

- Better search accuracy
- Better search previews
- Better navigation
- Better scalability

---

# 17. Why Recursive Chunking?

Recursive chunking preserves document structure.

Order

```
Paragraph

↓

Line

↓

Sentence

↓

Word
```

Large sections are automatically split when necessary.

---

# 18. Why 512 Tokens?

512 tokens provide a good balance between

- Context
- Retrieval accuracy
- Performance
- Memory usage

---

# 19. Why 64-Token Overlap?

Overlap prevents information near chunk boundaries from being lost.

It preserves context between neighbouring chunks.

---

# 20. Why SHA-256?

SHA-256 detects whether a note has changed.

Workflow

```
Save

↓

Calculate Hash

↓

Compare with Indexed Hash

↓

Same

↓

Skip Indexing

↓

Different

↓

Re-index
```

This avoids unnecessary embedding generation.

---

# 21. Why SwingWorker?

Generating embeddings takes time.

Running this task inside a SwingWorker keeps the editor responsive.

The user can continue using the application while indexing runs in the background.

---

# 22. Why Transactions?

Updating an index involves multiple database operations.

Transactions ensure that either

```
Everything succeeds

↓

COMMIT
```

or

```
Any failure

↓

ROLLBACK
```

This prevents partial indexes.

---

# 23. Why Dirty Flag?

The dirty flag tracks whether a note has unsaved changes.

It is used to

- Display the '*' indicator
- Warn before closing
- Decide whether saving is required

## 27.1 AI Chat Viva Questions

### Q19. What does the AI assistant do?

It lets a user chat with the currently open note. The user can ask for explanations or summaries, and the locally hosted generative model is instructed to ground its answers in that note.

### Q20. Is the AI assistant the same as semantic search?

No. Semantic search uses embeddings to retrieve and rank matching note chunks. AI chat uses a generative model to answer questions about the active note. Ordinary search stays separate and does not need a chat-model call.

### Q21. Why do you use the open note directly instead of RAG over the database?

The initial feature is deliberately limited to one note that the user has already opened. Passing its current editor content is simpler than retrieving across the entire note collection, and no new database schema is required. Multi-note RAG can be considered later.

### Q22. How do you handle context limits?

The application checks the note and recent conversation against a configured context budget. It must show a clear limitation or use an explicit bounded-context method for long notes rather than silently truncating them.

### Q23. Why is the sidebar collapsible?

It keeps the editor as the main workspace and lets users invoke AI only when needed. Collapsing the panel hides it without clearing the current in-memory conversation.

### Q24. Why is the chat model separate from EmbeddingGemma?

EmbeddingGemma generates vectors for semantic retrieval. A separate compatible generative/instruct model is needed to produce natural-language answers.

### Q25. What happens if the local model is unavailable?

The assistant shows an error. Note editing and ordinary semantic search remain usable, and DeepNote does not silently send note content to a cloud model.

# 30. One-Minute Architecture Explanation

If the examiner asks,

> "Explain your project."

the following explanation can be used.

---

DeepNote is an offline AI-powered semantic note-taking application developed using Java Swing.

Unlike traditional note-taking applications that search only for exact keywords, DeepNote allows users to search notes based on their meaning using vector embeddings.

When a user creates or edits a note, it is stored as a normal TXT file. These TXT files are the source of truth, so users always own and can access their notes outside the application.

When the user saves a note, DeepNote calculates a SHA-256 hash of its contents. If the hash matches the previously indexed version, no further processing is required. If the content has changed, a SwingWorker starts in the background so that the user interface remains responsive.

The background task reads the TXT file, splits it into meaningful chunks using LangChain4j's recursive document splitter, and generates embeddings for each chunk using Google's EmbeddingGemma model running locally through Ollama.

These embeddings, along with metadata such as the note ID, chunk order, chunk text and vector embeddings, are stored in PostgreSQL using the pgvector extension. The complete note itself is never stored in the database.

When the user performs semantic search, the query is converted into an embedding using the same embedding model. PostgreSQL compares this query embedding with stored chunk embeddings using vector similarity search. Matching chunks are grouped by note, ranked and displayed with a relevant snippet. Ordinary search does not invoke the generative model.

When a note is open, the user can optionally open the collapsible AI sidebar. DeepNote sends the active editor content, recent chat turns and the user's question to a separate local generative model through Ollama. A context manager checks the prompt budget, and the model is instructed to say when the note does not contain enough information. Generation runs in the background so the interface remains responsive.

When the user opens a search result, DeepNote opens the note and automatically scrolls to the matching section using the stored chunk text.

If Ollama is unavailable, the application automatically falls back to normal keyword search, ensuring that the search feature always remains usable.

Overall, the project demonstrates Java Swing, Object-Oriented Programming, JDBC, file handling, PostgreSQL, LangChain4j, Ollama, vector embeddings and semantic search within a clean layered architecture.
