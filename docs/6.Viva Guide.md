# 1. Introduction

This guide contains the important concepts, design decisions, trade-offs and commonly asked viva questions for DeepNote v0.1.

Its purpose is to help explain the project confidently during demonstrations and viva examinations.

---

# 2. Elevator Pitch (30–60 Seconds)

> DeepNote is an offline-first note-taking application targeting Java 25, JavaFX 27 and AtlantaFX 3.0.0. The current foundation stores ordinary TXT files, provides local keyword search and offers optional active-note Ollama chat. PostgreSQL, pgvector and semantic ranking are planned for a later phase.

---

# 3. Project Objective

> To develop an offline desktop note-taking application with portable TXT notes, local keyword search and optional private active-note chat, with semantic search planned for a later database phase.

---

# 4. Why This Project?

Traditional note-taking applications depend mainly on keyword matching.

Example

Searching

```
Vehicle
```

may not find

```
Car
```

The current foundation searches local titles and content by keyword. Meaning-based vector search is a later database-phase goal.

---

# 5. Why Java?

- Course requirement
- Strong OOP support
- JavaFX GUI with FXML
- JDBC database connectivity
- Platform independent
- Mature ecosystem

---

# 6. Why JavaFX and AtlantaFX?

- JavaFX provides the target desktop UI toolkit with FXML for larger layouts.
- Java controllers keep view coordination separate from business services.
- AtlantaFX 3.0.0 provides the dark theme foundation, while centralized CSS/design tokens own product styling.
- JavaFX `Task`/`Service` supports responsive background file and Ollama work.
- The current smoke foundation is implemented; the complete wireframe migration remains planned.

---

# 7. Why TXT Files?

TXT files are

- Portable
- Human readable
- Easy to edit outside DeepNote
- Easy to back up

TXT files remain the **Source of Truth**.

---

# 8. Why PostgreSQL later?

In the planned database phase, PostgreSQL will store

- Note metadata
- Categories
- Semantic chunks
- Embeddings

It is intended to support the **pgvector** extension required for future semantic search.

---

# 9. Why pgvector later?

In the planned database phase, pgvector will allow similarity search directly inside PostgreSQL.

Instead of comparing words, it compares embedding vectors.

---

# 10. Why Not Store Notes in PostgreSQL?

The complete note is stored as a TXT file because

- Users own their files
- Files remain portable
- Easier backup
- Database stays lightweight

---

# 11. Why Store Embeddings in PostgreSQL later?

Embeddings need

- Fast similarity search
- Vector indexing
- Metadata association

TXT files remain authoritative. The later database phase may add embeddings for efficient semantic search without changing the source files.

---

# 12. Why a future embedding utility?

The later database phase may use a utility library for

- Recursive chunking
- Token counting
- Embedding model integration

It will not control the application architecture.

---

# 13. Why EmbeddingGemma later?

Reasons

- Lightweight
- Runs locally
- Excellent retrieval performance
- Supported by Ollama
- Generates 768-dimensional embeddings

---

# 14. Why Ollama?

Ollama runs AI models locally.

Benefits

- Offline
- Private
- No API costs
- Fast local inference

---

# 15. Why Semantic Search later?

Keyword search requires exact words.

Semantic search could retrieve notes based on meaning, but it is not implemented or verified in the current foundation.

---

# 16. Why Chunking later?

A long note should not become one embedding.

Instead

```
Note

↓

Chunks

↓

Embedding per Chunk
```

Benefits

- Better search accuracy
- Better search previews
- Better navigation
- Better scalability

---

# 17. Why Recursive Chunking?

Recursive chunking preserves document structure.

Order

```
Paragraph

↓

Line

↓

Sentence

↓

Word
```

Large sections are automatically split when necessary.

---

# 18. Why 512 Tokens?

512 tokens provide a good balance between

- Context
- Retrieval accuracy
- Performance
- Memory usage

---

# 19. Why 64-Token Overlap?

Overlap prevents information near chunk boundaries from being lost.

It preserves context between neighbouring chunks.

---

# 20. Why SHA-256?

SHA-256 detects whether a note has changed.

Workflow

```
Save

↓

Calculate Hash

↓

Compare with Indexed Hash

↓

Same

↓

Skip Indexing

↓

Different

↓

Re-index
```

This avoids unnecessary embedding generation.

---

# 21. Why JavaFX Task/Service?

File, model and future database operations can take time. Running suitable work inside a JavaFX `Task` or `Service` keeps the JavaFX Application Thread responsive. The current Swing implementation may still use its legacy `SwingWorker` while migration is incomplete.

---

# 22. Why Transactions?

Updating an index involves multiple database operations.

Transactions ensure that either

```
Everything succeeds

↓

COMMIT
```

or

```
Any failure

↓

ROLLBACK
```

This prevents partial indexes.

---

# 23. Why Dirty Flag?

The dirty flag tracks whether a note has unsaved changes.

It is used to

- Display the '*' indicator
- Warn before closing
- Decide whether saving is required

### Encapsulation

Private fields with getters and setters.

### Abstraction

Services hide implementation details.

Example

```
SearchService.search()

↓

Will perform semantic search internally after the database phase
```

---

### Composition

A Note contains many Chunks.

---

### Interfaces & Runtime Polymorphism

`Searcher` is a common interface implemented by `VectorSearcher` and `TextSearcher`.

```
SearchService chooses

VectorSearcher

or

TextSearcher

at runtime
```

`SearchService` calls `Searcher.search()` without knowing which implementation is behind it — this is runtime polymorphism.

---

### MVC

The following mapping describes the transitional legacy Swing implementation only; the target view is JavaFX/FXML.

- Model → Data
- View → JavaFX/FXML UI
- Controller → Connects UI and Services

---

### Exception Handling

Custom exception: `NoteIndexingException`.

It distinguishes an indexing failure from an ordinary IO or SQL exception, so the UI can show a clear message while note editing continues normally.

# 27. Common Viva Questions

## Q1. What problem does your project solve?

It is intended to enable semantic search for offline notes later.

---

## Q2. Why is it called DeepNote?

Because it searches notes using semantic meaning instead of only keywords.

---

## Q3. Why use AI?

To generate vector embeddings used for future semantic search.

---

## Q4. Why not use ChatGPT or cloud APIs?

The application is designed to work completely offline.

---

## Q5. What is an embedding?

An embedding is a numerical vector that represents the meaning of text.

---

## Q6. What is chunking?

Breaking a long note into smaller meaningful sections before generating embeddings.

---

## Q7. Why not generate one embedding for the whole note?

A note may contain multiple topics.

Chunking improves retrieval accuracy.

---

## Q8. Why hash the note?

To detect changes efficiently and avoid unnecessary re-indexing.

---

## Q9. What happens when a note is saved?

1. Save TXT file.
2. Calculate SHA-256 hash.
3. Compare with stored hash.
4. If changed, regenerate embeddings.
5. Update PostgreSQL.

---

## Q10. What if Ollama is not running?

Planned semantic search becomes unavailable.

The application informs the user and falls back to keyword search.

---

## Q11. Why use LangChain4j?

It simplifies chunking and embedding integration while allowing us to keep our own application architecture.

---

## Q12. Why not use LangChain4j's EmbeddingStore?

We wanted complete control over our PostgreSQL schema and SQL queries.

LangChain4j is used only for chunking and embedding generation.

---

## Q13. Why not store complete notes in PostgreSQL?

TXT files are the primary storage.

The database stores only searchable metadata.

---

## Q14. What normalization is used?

Third Normal Form (3NF).

---

## Q15. Which OOP concepts are demonstrated?

- Classes & Objects
- Encapsulation
- Abstraction
- Composition
- Interfaces & Runtime Polymorphism
- Modularity
- MVC

---

## Q16. What makes DeepNote different from Notepad?

Notepad supports only keyword search.

DeepNote is planned to support semantic search using vector embeddings after the database phase.

## 27.1 AI Chat Viva Questions

### Q19. What does the AI assistant do?

It lets a user chat with the currently open note. The user can ask for explanations or summaries, and the locally hosted generative model is instructed to ground its answers in that note.

### Q20. Is the AI assistant the same as semantic search?

No. The current search is local keyword search and does not call the chat model. Future semantic search will use embeddings to retrieve and rank matching note chunks. AI chat uses a generative model to answer questions about the active note.

### Q21. Why do you use the open note directly instead of RAG over the database?

The initial feature is deliberately limited to one note that the user has already opened. Passing its current editor content is simpler than retrieving across the entire note collection, and no new database schema is required. Multi-note RAG can be considered later.

### Q22. How do you handle context limits?

The application checks the note and recent conversation against a configured context budget. It must show a clear limitation or use an explicit bounded-context method for long notes rather than silently truncating them.

### Q23. Why is the right-side AI panel collapsible?

It keeps the editor as the main workspace and lets users invoke AI only when needed. Collapsing the panel hides it without clearing the current in-memory conversation.

### Q24. Why is the chat model separate from EmbeddingGemma?

EmbeddingGemma generates vectors for semantic retrieval. A separate compatible generative/instruct model is needed to produce natural-language answers.

### Q25. What happens if the local model is unavailable?

The assistant shows an error. Note editing and local keyword search remain usable, and DeepNote does not silently send note content to a cloud model.

# 30. One-Minute Architecture Explanation

If the examiner asks,

> "Explain your project."

the following explanation can be used.

---

DeepNote is an offline-first note-taking application whose target UI uses JavaFX 27, FXML, Java controllers and AtlantaFX 3.0.0. The smoke foundation is implemented; the complete wireframe migration is not yet complete.

The current foundation searches local TXT-backed note titles and content by keyword. Semantic/vector search is a planned database-phase capability and must not be presented as currently working.

When a user creates or edits a note, it is stored as a normal TXT file. These TXT files are the source of truth, so users always own and can access their notes outside the application.

When the user saves a note, DeepNote calculates a SHA-256 hash of its contents. Database indexing is planned for a later phase. In the JavaFX target, suitable blocking operations use `Task`/`Service` so the JavaFX Application Thread remains responsive.

The later database phase may read the TXT file, split it into chunks and generate embeddings locally through Ollama. That pipeline is planned, not part of the current foundation.

The planned database phase will store embedding metadata and vectors in PostgreSQL using pgvector; the complete note will remain outside the database.

The current search is local keyword search and does not invoke the generative model. Later, PostgreSQL may compare query embeddings with stored vectors and provide ranked results.

When a note is open, the user can optionally open the collapsible right-side AI panel. DeepNote sends the active editor content, recent per-note chat turns and the user's question to a separate local generative model through Ollama. A context manager checks the prompt budget, and JavaFX background work keeps the interface responsive.

When the JavaFX migration is complete, homepage search results will open the selected note in the same Home tab or activate its existing note tab. Ranked chunk navigation is deferred with semantic search.

If Ollama is unavailable, local note editing and keyword search remain usable; the app does not use a cloud fallback.

Overall, the project demonstrates JavaFX, FXML, Java controllers, Object-Oriented Programming, TXT file handling and local Ollama integration within a clean layered architecture, with PostgreSQL/pgvector reserved for a later phase.
